# Proboi Privacy: точные факты для презентации и план релиза

Дата фиксации: 27 июля 2026 года.

## Как читать цифры

- **Измерено** — сохранено в frozen-отчётах проекта.
- **Рассчитано** — вычислено из измеренных значений; это не отдельный нагрузочный тест.
- **Предлагается** — следующий план. Это ещё не выполненный результат.

## Главный вывод

Контур локальной деперсонализации, шифрования и fail-closed защиты реализован и
протестирован. Последний ML-кандидат v15 не прошёл quality и drift gates и имеет
статус `research-rejected`. Референсный v7 также не прошёл production gates.
Production default не менялся. Новые веса пока нельзя выдавать за готовую
production-модель.

Безопасный следующий шаг — запустить текущие правила и Natasha в закрытом пилоте,
а GLiNER использовать только в shadow-режиме. Для включения GLiNER в production
нужны клиентский gold-корпус, новый preregistered цикл v16, полный release gate и
нагрузочный тест на целевой инфраструктуре.

Предположение: один пользователь отправляет один документ в минуту; расчёт по p95

## Слайд 8. Что происходит, если модель не уверена

### Текущее поведение

1. GLiNER возвращает сущность только если score не ниже настроенного threshold.
   Для frozen evaluation v7 это 0,60; для v15 — 0,65.
2. Совпадение ниже threshold GLiNER отбрасывает.
3. Тот же текст независимо проверяют локальные правила и Natasha. Если они нашли
   сущность, она всё равно заменяется токеном.
4. Если ни один слой не нашёл сущность, система не знает, что был пропуск. Такой
   фрагмент может остаться в тексте. Именно поэтому новый ML-вес нельзя включать в
   production до клиентского recall gate.
5. Если обязательный GLiNER/sidecar не загрузился, упал или превысил timeout,
   внешний egress блокируется. Сырой текст не отправляется.
6. При пересечении результатов точное правило имеет приоритет.
7. Если произошёл false positive, текст будет избыточно токенизирован, но оригинал
   можно точно восстановить из локального зашифрованного Token Vault.

### Что добавить перед production

- Shadow-режим: модель ничего не решает, только пишет обезличенные метрики.
- Все high-risk документы в пилоте проходят локальную проверку человеком.
- Числовую «серую зону» score выбрать только на клиентском dev; до этого её нельзя
  придумывать.
- Любая ошибка обязательного компонента, vault или ключей — блокировка отправки.

## Слайд 9. Шифрование и контур предприятия

Этот материал лучше разделить на три экрана.

### 9А. Данные в покое

- Для каждого объекта создаётся отдельный DEK.
- Данные шифруются AES-256-GCM.
- IV: 12 байт.
- Authentication tag: 16 байт.
- DEK оборачивается AES-KW.
- KEK восстанавливается через scrypt: `N=65 536`, `r=8`, `p=1`.
- Windows: DPAPI user-scope.
- Linux/on-prem: защищённый keyfile + AES-GCM.
- Без явно настроенного защищённого ключевого контура система работает
  fail-closed.

### 9Б. Данные перед выходом наружу

- PII заменяется до сетевого туннеля.
- Во внешний сервис уходит деперсонализированный текст.
- Карта токенов остаётся в локальном encrypted Token Vault.
- Audit receipt содержит счётчики, профиль и hash, но не исходный PII.
- Система поддерживает полностью изолированный on-prem режим.

### 9В. Отказы и восстановление

- Sidecar timeout/down → egress блокируется.
- Невалидный или отсутствующий профиль → egress блокируется.
- Подмена encrypted vault обнаруживается.
- Неверный user/machine scope ключа не расшифровывает vault.
- Разделение арендаторов проверено.
- После рестарта токены восстанавливаются точно.

## Слайд 10. Почему модель пока не в production

- v15 не прошёл precision, recall, FIELD, safe-document, clean-negative и drift.
- v7 не прошёл recall, FIELD, clean-negative, long-document smoke и latency.
- Нет клиентского document-level gold.
- Нет независимой двойной разметки и adjudication.
- Нет frozen client test и client OOD.
- Не завершены security/privacy/license reviews владельцем.
- Не выбрана целевая инфраструктура.
- Не проведены load test и rollback exercise.
- Не утверждены monitoring, drift policy и incident runbook.

Текущий честный статус: **технологический контур готов к закрытому пилоту;
новый ML-вес не готов к production**.

## Что делать дальше

### Шаг 1. Запустить безопасный закрытый пилот — предлагается

- Production decision пока принимают rules + Natasha.
- v7 и v15 работают только в shadow-режиме и не управляют egress.
- Пилот: 10 внутренних пользователей, 2 недели, минимум 500 обработанных
  документов.
- Для high-risk документов — обязательная локальная проверка результата человеком.
- Исходные документы не покидают клиентский контур.
- Любая ошибка обязательного компонента блокирует отправку.

### Шаг 2. Собрать клиентский gold — предлагается

Минимальный пакет: **1 200 клиентских документов**:

- 600 train;
- 200 selection dev;
- 200 frozen client test;
- 200 untouched client OOD из другого периода или источника.

Правила:

- split по источнику, документу, человеку, организации, объекту и template family
  до обучения;
- два независимых разметчика;
- отдельный adjudicator для разногласий;
- минимум 200 gold-сущностей каждого типа `PER`, `ORG`, `ADDR`, `FIELD`;
- минимум 200 clean-negative документов;
- минимум 200 FIELD hard-negative документов;
- минимум 50 длинных документов;
- raw-корпус хранится только в зашифрованном клиентском контуре и не коммитится в
  Git.

Это предлагаемый release minimum, а не уже собранные данные.

### Шаг 3. Новый цикл v16 — предлагается

Не продолжать v15 и не повторять margin/L2 schedule.

1. Вернуться к immutable v7 как anchor.
2. Сначала измерить, какие FIELD пропуски возникают уже на низком candidate
   threshold и какие false positive имеют высокий score.
3. Если низкий threshold даёт нужный candidate recall, использовать двухступенчатую
   схему:
   - v7 генерирует FIELD-кандидаты с высокой полнотой;
   - отдельный маленький FIELD-verifier отбрасывает ложные кандидаты по контексту.
4. PER/ORG/ADDR и общий encoder не переобучать без доказанной необходимости.
5. До inference зафиксировать `experiment-plan.json`, данные, seed, budget,
   единственный candidate, drift caps и stop rule.
6. Обучить один candidate и остановиться при первом failed gate.

Почему этот путь: v15 пытался одновременно исправить FIELD через общий loss и
получил сильный drift, но почти не изменил recall. Отдельный verifier уменьшает
влияние на уже работающие PER/ORG/ADDR.

### Шаг 4. Обязательные gates v16

До public/OOD:

- targeted precision ≥90%, recall ≥97%;
- combined precision ≥90%, recall ≥97%;
- `PER`, `ORG`, `ADDR`, `FIELD` recall ≥97%;
- direct identifiers recall ≥97%;
- safe-document rate ≥97%;
- targeted clean-negative rate ≥95%;
- preservation overall и каждый тип не ниже v7;
- component drift не выше заранее зафиксированных caps.

Только после этого:

1. fresh-process smoke ×2;
2. frozen public regression ровно один раз;
3. CPU performance: median, p95 и RSS не хуже baseline более чем на 10%;
4. full privacy flow;
5. untouched client OOD.

Любой failed gate → `research-rejected`, production default не менять.

### Шаг 5. Нагрузочный и эксплуатационный gate

- Выбрать точный CPU/RAM/OS сервера.
- Проверить 1, 4, 8 и 16 параллельных клиентов.
- Длительность каждого уровня: не менее 30 минут.
- Error rate: 0 для privacy-операций.
- Утечка raw PII: 0.
- Проверить cold start, restart, очередь, timeout, sidecar crash и vault failure.
- Выполнить rollback exercise на предыдущий production default.
- Зафиксировать deployment manifest, владельца, мониторинг и incident runbook.

### Шаг 6. Выпуск

После прохождения всех gates:

1. shadow на полном потоке;
2. canary 5%;
3. 25%;
4. 50%;
5. 100%.

На каждой ступени минимум 24 часа стабильной работы. Любой raw-PII incident,
ошибка vault/ключей или превышение согласованного p95 → немедленный rollback.

## Что говорить руководству одной фразой

«Мы завершили исследовательский цикл и построили рабочий локальный контур
деперсонализации с шифрованием и fail-closed защитой. Последний ML-кандидат честно
не прошёл production-критерии, поэтому не включён. Следующий этап — закрытый
shadow-пилот, клиентский gold-корпус и один целевой v16-цикл с отдельной проверкой
FIELD; после quality, security и load gates возможен поэтапный production rollout».

## Что нельзя говорить

- «Модель готова к production».
- «Все проверки пройдены».
- «Поддерживается N одновременных пользователей» без load test.
- «Скорость 3 000 генеративных токенов/с»: модель не генерирует текст.
- «Модель не пропускает PII, если не уверена»: низкий score сам по себе сейчас не
  блокирует документ.
- «Обучались только на полностью аудированных данных»: upstream-корпус исходной
  `gliner-pii-base-v1.0` внутри проекта не аудирован.
